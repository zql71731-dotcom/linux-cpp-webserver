# TinyWebServer（C++ 轻量级 Web 服务器 · 学习与改造）

基于 [qinguoyi/TinyWebServer](https://github.com/qinguoyi/TinyWebServer) 的学习与改造。
原项目是一个使用 epoll + 线程池 + 定时器的 C++ Web 服务器。
## 我做了什么

 - **新增 `/hello` 路由，改为由代码直接构造响应。**
  原项目把 URL 改写成 `hello.html`，再用 `open` 打开文件、`mmap` 映射到内存，返回一个 HTML 页面。
  改为在内存中直接拼出 `{"msg":"ok"}`，加上 HTTP 头返回，不再读取磁盘上的文件。
  验证：`strace -f -e trace=openat` 记录系统调用，其中 `hello.html` 出现 **0** 次，
  作为对照，`judge.html` 出现 **2** 次（`/` 走的是读文件路径）。
- **日志输出改到 `logs/` 目录。**
  原先日志写在项目根目录下（如 `2026_10_30_ServerLog`），压测时 10 秒可写 145MB，文件大量堆在仓库根目录；
  且 `.gitignore` 中的 `*_ServerLog` 匹配不到日志切分产生的 `.1` 文件，导致它一直出现在 `git status` 的未跟踪列表里。
  改动：启动时 `mkdir("./logs")`，日志路径改为 `./logs/ServerLog`，`.gitignore` 改为 `*_ServerLog*`。
  结果：日志集中在 `logs/` 目录下，仓库根目录保持干净。
- **压测与瓶颈定位。**
  编写 `run.sh`，一条命令完成「编译 → 启动 → 压测 → 结果写入 `logs/bench.txt`」。
  用控制变量法做了四组对比：

  - 关闭日志：3019 → 3116，提升很小
  - 丢弃 `stderr` 调试输出：3116 → 3965（**+27%**），主要来源
  - 工作线程 8 → 16：3937，无变化
  - `listen` backlog 5 → 128：4068，无变化

  线程数翻倍无效，说明瓶颈在主线程：默认 Proactor 模式下，`accept`/`recv`/`writev`
  全部由主线程执行，线程池只分担 HTTP 解析。
- **修复线程池队列满时任务被静默丢弃的问题。**
  `threadpool::append()` / `append_p()` 在队列满时返回 `false`，但 `webserver.cpp` 里三处调用都没有检查返回值：
  Proactor 分支下这个连接会一直挂到定时器超时；Reactor 分支下主线程会卡在随后的 `while (true)`
  忙等里，整个服务器失去响应。
  改动：三处都改为判断返回值，失败时记录日志并调用 `deal_timer()` 关闭连接。
  验证：把队列上限临时调成 4，用 `webbench -c 100` 压测，日志中出现 47 条
  `task queue is full, close fd N`，服务器没有挂死。
- **修复 CGI 参数解析中的栈溢出。**
  `do_request()` 的 CGI 分支用 `char name[100]` 接收用户名，但复制循环没有长度检查：
  发送 300 字节的 `user=` 字段即可覆盖栈上相邻数据，实测服务器进程直接崩溃，日志停在请求体那一行。
  改动：改用 `strchr` 定位分隔符，先计算长度并校验，非法则返回 `BAD_REQUEST`，再用 `memcpy` 复制。
  顺带修正了密码偏移：原代码从 `&` 之后跳过 10 个字符，而 `&passwd=` 只有 8 个字符，
  会导致密码永远缺少前两位、登录永远失败。
  验证：同一个 payload 修复前返回空响应且进程退出，修复后返回 404 且服务正常。
- **修复 CGI 注册流程中的 SQL 注入与堆溢出。**
  注册分支用 `strcat` 把用户名/密码直接拼进 SQL，存在两个问题：
  一是 **SQL 注入**——用户名里带单引号即可破坏 SQL 语句结构；
  二是 **堆溢出**——`malloc(sizeof(char) * 200)` 装不下最长的输入：
  SQL 模板 43 字节 + 用户名 99 + 分隔 4 + 密码 99 + 结尾 2 + `'\0'` = **248 字节**，`strcat` 会写穿堆内存。
  改动：先用 `mysql_real_escape_string` 转义，再用 `snprintf` 写入固定大小的栈缓冲区（512 字节），
  并检查返回值确认未被截断；同时去掉原来 `malloc` 后从不 `free` 的内存泄漏。
  验证：发送 99 字节用户名 + 99 字节密码，修复前进程崩溃（glibc 报 `malloc(): corrupted top size`），
  修复后返回 404 且服务正常；用户名带单引号也能正常注册。

## 压测数据

环境：VMware Ubuntu（16 vCPU），目标 `/`，客户端与服务端运行在**同一台虚拟机**上。

> **关于测量有效性的说明**：压测客户端与服务端同机运行，客户端自身也占用 CPU 并与服务端竞争，
> 因此 QPS 的**绝对值偏保守**（换更轻量的客户端会更接近上限，见下方两个工具的对比）。
> 但各组对比实验的环境完全一致，**相对结论（谁快谁慢、加线程是否有效）仍然成立**。
> 若要得到更接近真实上限的数字，应把压测客户端部署到另一台机器。

### 一、并发—吞吐曲线（ab）

`ab -n 10000 -c N`，服务端以 `-l 1` 启动（关闭日志）。

| 并发 | QPS | 平均延迟 | P99 | 失败 |
|---|---|---|---|---|
| 10 | 4623 | 2.2 ms | 3 ms | 0 |
| 50 | 4561 | 11.0 ms | 14 ms | 0 |
| 100 | 4583 | 21.8 ms | 25 ms | 0 |
| 200 | 4251 | 47.1 ms | 44 ms | 0 |
| 400 | 2557 | 156 ms | **4348 ms** | 0 |

**三条结论：**

1. **饱和点在 10 并发**——10 个并发就到 4623 QPS，加到 100 个仍是 4600 左右。
   说明单次请求的处理成本很低，瓶颈**极度集中**（一个线程）。
2. **并发 ×10，QPS 不变、延迟 ×10**——这是典型的**排队**特征，不是计算慢。
   各组数据都满足 `并发 ÷ QPS = 平均延迟`（利特尔法则）。
3. **400 并发时过载**：QPS 掉到 2557，P99 从 25 ms 涨到 **4.3 秒**。
   原因是 `listen` 的 backlog 只有 128，连接挤爆 accept 队列后内核丢弃、客户端 TCP 重传，
   重传又占用资源，进入恶性循环（`ss -lnt` 在 100 并发时已观测到队列表 `Recv-Q` 顶到 97/128）。

### 二、控制变量实验（webbench）

`webbench -c 100 -t 10`，基线 3019 QPS。

| 配置 | QPS | 说明 |
|---|---|---|
| 日志开 | 3019 | 基线 |
| 日志关 | 3116 | 只涨 3%，日志不是瓶颈 |
| 日志关 + 丢弃 stderr | 3965 | **+27%**，主要来源 |
| 工作线程 8 → 16 | 3937 | 无变化 → 工作线程不是瓶颈 |
| `listen` backlog 5 → 128 | 4068 | 无变化 → 连接队列不是瓶颈 |

**两个工具的差异**：同一配置下 `ab` 测得 4583 QPS、`webbench` 测得 3965，差约 14%。
原因是客户端自身的开销不同——`webbench` fork 100 个进程，`ab` 更轻量。**这也印证了同机压测的局限：客户端越重，测出的 QPS 越低。**

### 三、瓶颈结论

**瓶颈在主线程。** 默认 `actor_model=0`（Proactor）下，`accept` / `recv` / `writev` / `close`
全部由主线程同步执行，线程池只分担 HTTP 解析。证据三条：

- 工作线程 8 → 16，QPS 无变化
- 去掉主线程内的 `stderr` 调试输出，QPS 提升 27%
- 并发—吞吐曲线在 10 并发即饱和，增加并发只增加排队延迟

**优化方向**：`SO_REUSEPORT` 让多线程各自 accept；把读写交给工作线程（真 Reactor）；
定时器换最小堆（`add_timer` 从 O(n) 到 O(log n)）。

## 编译与运行

    make                    # 编译
    ./server                # 启动，默认端口 9006
    ./server -p 9090        # 指定端口启动
    ./run.sh                # 一键：编译 + 启动 + 压测（结果写入 logs/bench.txt）

启动后浏览器访问 http://127.0.0.1:9006/

## 已知瓶颈与改进方向

主线程承担全部 socket I/O。改进方向：把读写也交给工作线程（真 Proactor），
或使用 `SO_REUSEPORT` 让多个线程各自 accept。

## 已知问题（读代码时发现，未修改）

- `add_status_line()` / `add_headers()` 的返回值没有被检查。当前写缓冲区 1024 字节、
  正常响应头约 60 字节，实际触发不了；但若以后增加自定义响应头需要重新评估。
- 不支持 HTTP pipelining：一次 `recv` 读到多个请求时，`init()` 会清空读缓冲区，只处理第一个。
- 读缓冲区固定 2048 字节，请求行加头部超过该长度的请求会被 `read_once()` 直接拒绝。
