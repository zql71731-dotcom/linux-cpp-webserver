## 一、项目简介（三个版本，按场合用）

### 30 秒版 —— 自我介绍里带过

> 这个项目是在开源项目 TinyWebServer 基础上做的 C++ Web 服务器，跑在 Linux 上，核心是 epoll 事件驱动加线程池。
> 我主要做了三件事：压测并定位性能瓶颈在主线程、修了两个缺陷（其中一个能导致服务器崩溃）、以及工程上的整理。
> 压测 QPS 约 4000。

### 60 秒版 —— 「介绍一下你的项目」

> 这是我在开源项目 TinyWebServer 基础上做的。它是一个用 C++ 写的轻量级 Web 服务器，我这份跑在 Linux 上，
> 核心是 epoll 事件驱动加线程池，支持静态资源访问、登录注册、连接超时管理，数据用 MySQL 连接池。
>
> **我主要做了三件事。**
>
> 第一是压测和瓶颈定位。用 webbench 测到 QPS 大概 4000，再用控制变量实验——分别调日志开关、stderr 输出、
> 线程数、backlog——定位到瓶颈在主线程的 I/O，不在线程池。
>
> 第二是修了三个缺陷。一个是线程池 append 的返回值，三处调用都没有检查，队列满时任务会被丢掉，
> Reactor 分支还会让主线程死循环；我改成检查返回值、失败就记录日志并关闭连接。
> 另一个是 CGI 参数解析的栈溢出，构造一个特制请求就能让服务器崩溃，我复现之后加了边界校验。
> 第三个是注册流程里的 SQL 注入和堆溢出——拼接 SQL 的缓冲区只分配了 200 字节，而最长输入需要 248 字节，
> 我用转义加 snprintf 一起修掉了。三个都做了回归验证。
>
> 第三是工程整理：日志归档到单独目录、写了一键压测脚本、把 Makefile 迁移到 CMake、补了 README 和已知问题清单。

**说完就停，等追问。**

### 2 分钟版 —— 对方明显感兴趣时

在 60 秒版基础上，每个点展开一句：

- **瓶颈**：三条独立证据——线程 8→16 无变化、去掉 stderr 输出 QPS 涨 27%、`ss` 看到 accept 队列顶在 97/128
- **栈溢出**：`char name[100]` 后面是没边界检查的复制循环，300 字节的用户名字段就能覆盖栈上返回地址
- **SQL 注入 + 堆溢出**：`strcat` 直接拼 SQL；`malloc(200)` 装不下 248 字节的最长输入，99+99 字节即崩溃
- **队列满**：`append` 返回 false 但三处都没接，Reactor 分支会卡在随后的 `while(true)` 忙等里

## 二、项目类问题（几乎必问）

### 1. 介绍一下你的项目
→ 用上面的 60 秒版。**重点是「我做了什么」，不是「项目有什么功能」。**

### 2. 这个项目最难的地方是什么
答题方向：
> 最难的是**判断瓶颈在哪**。一开始我以为是日志，关掉只涨 3%，排除了；再试 stderr，涨 27%；
> 然后试加线程，没变化——这才确定瓶颈在主线程。**每一步都是先假设、再做实验排除。**

### 3. 你做了什么改造？为什么做？
→ 三条：`/hello` 直接构造响应（不读磁盘）、日志归档、压测脚本。
**每条都说「原来怎样 → 问题是什么 → 改成什么 → 结果」。**

### 4. QPS 多少？瓶颈在哪？怎么证明的？
> 约 4000（100 并发、10 秒）。瓶颈在主线程。三条证据：
> ① 工作线程 8→16 无变化；② 去掉主线程里的 stderr 输出后 QPS 涨 27%；
> ③ `ss -lnt` 看到 accept 队列持续顶在 97/128，说明主线程取连接跟不上。
> 根因是默认 Proactor 模式下 `recv`/`writev` 全在主线程，线程池只分担解析。

### 5. 那个栈溢出怎么发现的？怎么修的？
> 读 `do_request()` 的 CGI 分支时，看到 `char name[100]` 后面是一个 `for` 循环，复制到遇到 `&` 为止，
> 没有长度检查。我构造了一个 300 字节的 user 字段发过去，服务器直接崩了，日志停在请求体那一行。
> 改成先用 `strchr` 找分隔符、算长度、判断是否越界，越界就返回 `BAD_REQUEST`，再 `memcpy`。
> 修复后同样的请求返回 404，服务正常。

### 6. 注册流程里的 SQL 注入和堆溢出是怎么回事
> 注册分支用 `strcat` 把用户名和密码直接拼进 SQL，我发现两个问题：
>
> **一是 SQL 注入**：用户名里带单引号就能破坏语句结构，比如 `a','b`。
>
> **二是堆溢出**：我先算了一下最坏长度 —— SQL 模板 43 字节 + 用户名 99 + 分隔 4 + 密码 99 + 结尾 2 + `'\0'` 1
> = **248 字节**，而代码只 `malloc` 了 200。发 99 字节用户名 + 99 字节密码，进程直接崩溃，
> glibc 报 `malloc(): corrupted top size`。
>
> 修复：用 `mysql_real_escape_string` 转义防注入，用 `snprintf` 写进 512 字节的栈缓冲区并检查是否被截断，
> 顺手去掉了 `malloc` 后从不 `free` 的泄漏。
>
> 验证：修复前必崩的 payload，修复后返回 404 且服务正常；带单引号的用户名也能正常注册。

### 7. 队列满那个问题具体是什么
> `append` 队列满时返回 false，但 `webserver.cpp` 里三处调用都没有检查返回值。
> Proactor 分支下连接会挂到定时器超时；Reactor 分支下主线程会卡在后面的 `while(true)` 忙等里，整个服务失去响应。
> 改成检查返回值、失败就记日志并调 `deal_timer()` 关闭连接。
> 验证方式是把队列上限临时调成 4，用 webbench 压，日志里出现 47 条 drop 记录。

### 8. 如果让你继续优化，你会做什么
> ① 用 `SO_REUSEPORT` 让多个线程各自 accept，把 accept 并行化；
> ② 把 socket 读写也交给工作线程（真正的 Reactor），主线程只做分发；
> ③ 定时器从升序链表换成最小堆，`add_timer` 从 O(n) 降到 O(log n)。

### 9. 这个项目有什么不足
**这题要主动答，别等对方挖**（README 里有清单）：
> ① 不支持 HTTP pipelining，一次读到多个请求只处理第一个；
> ② 读缓冲区固定 2048 字节，超长请求会被拒；
> ③ `add_status_line`/`add_headers` 的返回值没检查（评估过，当前缓冲区 1024、响应头约 60 字节，触发不了）；
> ④ `do_request` 里的 `mysql` 是启动时取出的成员变量，用完已归还连接池，后续使用属于「复用已释放的连接」，
>    目前靠 `m_lock` 串行化才没出问题。
