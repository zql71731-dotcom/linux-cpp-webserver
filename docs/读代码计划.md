## 第一轮：服务器怎么站起来（约 1.5 小时）

**读**：`main.cpp` 全部 41 行 + `webserver.cpp:36-108`（init / trig_mode / log_write / sql_pool / thread_pool）

**关注**：启动时按顺序做了哪几件事？

```
parse_arg    解析命令行
init         保存配置
log_write    初始化日志（mkdir logs + Log::init）
sql_pool     建 MySQL 连接池（8 条）
thread_pool  new threadpool(8 个线程)
trig_mode    决定 LT/ET
eventListen  socket → bind → listen → epoll_create → addfd → socketpair → 注册信号
eventLoop    进入死循环
```

**自测**（不看代码）：

1. 服务器启动一共做了几件事？按顺序说
2. `listen(fd, 128)` 第二个参数是什么？
3. 为什么要有 `socketpair`？它用来干什么？

## 第二轮：一个连接怎么进来（约 2 小时）

**读**：`webserver.cpp:413-455`（eventLoop）+ `220-263`（dealclientdata）+ `300-412`（dealwithread / dealwithwrite）

**关注**：`epoll_wait` 返回后，怎么判断该走哪个分支？

```
sockfd == listenfd              → dealclientdata（accept）
events & (EPOLLRDHUP|HUP|ERR)   → 关连接 + 删定时器
sockfd == pipefd[0]             → dealwithsignal（信号）
events & EPOLLIN                → dealwithread
events & EPOLLOUT               → dealwithwrite
```

**还要看懂**：`dealwithread` 里 reactor 和 proactor 两条路的分歧（默认走 proactor）。

**自测**：

1. `epoll_wait` 返回后，有哪几种事件类型？各自的处理函数是哪个？
2. `dealclientdata` 在 LT 和 ET 下分别怎么 accept？
3. proactor 分支里，主线程做了什么、worker 做了什么？
4. reactor 分支里那个 `while(true)` 是在等什么？

## 第三轮：线程池（约 1.5 小时）

**读**：`threadpool/threadpool.h` 全部 152 行

**关注**：三个成员 + 两个函数

```
m_workqueue      std::list<T*>      任务队列
m_queuelocker    pthread_mutex_t    保护队列
m_queuestat      sem m_queuestat    可用任务数，初始 0

append / append_p   lock → push_back → unlock → post()
run()               wait → lock → front/pop_front → unlock → process()
```

**自测**：

1. 为什么队列既要锁又要信号量？各解决什么？
2. 信号量初始值为什么是 0？负值代表什么？
3. `front()` 和 `pop_front()` 为什么都要在锁里？
4. reactor 模式的 worker 做了什么额外的事？（`read_once` / `write`）

## 第四轮：HTTP 从字节到响应（约 3 小时，最重要）

**读**：`http_conn.cpp` 的
`init(113)` / `read_once(198)` / `parse_line(164)` / `parse_request_line(242)` /
`parse_headers(290)` / `parse_content(330)` / `process_read(342)` /
`do_request(388)` / `process_write(643)` / `write(538)` / `process(712)`

**关注一条链**：

```
read_once       recv 到 m_read_buf，m_read_idx 往后走
parse_line      从 m_checked_idx 找 \r\n，切出一行
process_read    状态机：请求行 → 头 → 空行 →（有 body 才进 CONTENT）
do_request      算路径 / CGI / 404 / 你的 /hello → 返回一个 HTTP_CODE
process_write   按 code 拼响应头 + 组 iov
write           writev 发出去，处理部分写
process         上面这一整串的调度者
```

**重点搞懂三个索引**：`m_read_idx`（写指针）、`m_checked_idx`（读指针）、`m_start_line`（行首）。

**自测**：

1. 半包时，新数据追加到哪里？解析从哪里继续？
2. `parse_headers` 怎么判断「头结束了」？
3. `do_request` 返回值有几种？分别对应 `process_write` 的哪个分支？
4. `m_iv[0]` 和 `m_iv[1]` 分别装什么？为什么静态文件要用两个 iov？
5. `write` 里 `bytes_to_send <= 0` 之后做了什么？如果没发完呢？

## 第五轮：定时器（约 1.5 小时）

**读**：`timer/lst_timer.cpp` 的
`add_timer(20)` / `adjust_timer(40)` / `del_timer(65)` / `tick(96)` /
`init(148)` / `addfd(163)` / `sig_handler(180)` / `addsig(190)` /
`timer_handler(202)` / `cb_func(218)`

**关注触发链**：

```
alarm(5) → SIGALRM → sig_handler（只 write 一个字节进管道）
        → epoll 发现 pipefd 可读 → dealwithsignal → timeout = true
        → timer_handler → tick() → alarm(5) 重新上闹钟
```

**自测**：

1. 定时器用的什么结构？插入/删除的复杂度分别是多少？
2. `tick()` 为什么遇到第一个未过期的就 break？
3. 为什么信号处理函数里不直接调 `tick()`？
4. 「惰性删除」在这个项目里体现在哪两处？
5. `adjust_timer` 什么时候被调用？

## 读的技巧

1. **别从头读到尾**，按上面的顺序顺着「一个请求」走
2. **每读一个函数，在旁边写一句话**（注释或纸上）
3. **读不懂的先标问号**，继续往下，读完一轮再回来
4. **配合 gdb 打断点**看实际执行顺序（可选，但很有效）
5. **读完一轮，合上代码画一遍流程图**

## 过关标准

**20 个自测问题，能答出 15 个以上，就算读透了。**

答不出的，就是还没懂的地方——把那些行再读一遍。
